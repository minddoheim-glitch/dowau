# 도와랩스 자체 뉴스레터 — 첫 구현

긱어스 서비스 자체를 임베드하거나 복제하지 않고, 기존 홈페이지에 독립적인 뉴스레터 기능을 추가한다. 기존 게시물·회원·수신 동의는 자동 이전하지 않는다. 현재 운영 반영·DB 생성·외부 메일 발송은 하지 않았다.

## 범위

- `/#newsletter`: 이메일 구독, 동의, 개인정보 안내, 칼럼 보관함. 홈 안내 배너와 사이드바 메뉴.
- 이메일 확인 후 가입 확정(24시간), 해지 링크, 동일 칼럼 중복 발송 방지.
- 링크 미리보기/보안 스캐너의 GET 요청은 구독 확인·해지를 실행하지 않는다. 사람이 버튼을 눌러 POST해야 변경된다. One-Click 해지 POST도 지원.
- 발송은 승인·공개한 **칼럼**만 허용. 저널링은 제외. 첫 칼럼은 아직 미등록.
- 기존 홈페이지와 별도 Git worktree에 작업. 기존 글·후기·코칭 링크 보존.
- Cloudflare Pages Functions + D1용 서버 후보. 스티비 구독자 요금제에 의존하지 않는 구조. Resend는 교체 가능한 발송 어댑터이며, 실제 대량 발송 이용 조건·발송량·비용·도메인 인증을 확인한 후 선택해야 한다. 무제한 무료 발송을 보장하지 않는다.

## 로컬 검증

Node 24 이상. 별도 npm 패키지 설치 없음.

```
npm test
npm run build
npm run preview
```

`http://127.0.0.1:5193/#newsletter`. 로컬 미리보기는 항상 신청 저장·외부 발송을 하지 않는다. 서비스 미연결 시 가짜 성공이나 브라우저 localStorage 저장으로 대체하지 않는다. 테스트는 인메모리 SQLite와 모의 발송 응답만 사용한다.

## 배포 후보

Cloudflare Pages: build `npm run build`, output `dist`, Functions directory `functions`. `newsletter/schema.sql`은 운영 대상에 검토 후 한 번 적용, `DB` D1 binding 필요. 기존 사이트 도메인 변경 및 이전은 별도 검토해야 한다. Vercel에는 이 Cloudflare Functions가 그대로 실행되지 않으므로 현재 운영 프로젝트에 바로 올려서 작동한다고 주장하면 안 된다.

공개 디렉터리는 `dist`만 사용한다. 저장소 전체를 정적 호스팅하지 않는다. schema, source, 운영 기록, 비밀값을 정적 파일로 노출하지 않는다. Cloudflare용 `/class` redirect를 빌드에 보존한다. 기존 www → apex 도메인 정규화는 신규 호스트에서 확인해야 한다.

### 서버 설정

다음 항목을 계정의 비밀 설정/환경변수에 넣는다. 채팅이나 GitHub·브라우저 JS에 키를 붙여넣지 않는다.

| 설정 | 용도 |
|---|---|
| `NEWSLETTER_ENABLED` | 기본 미설정/false, 신청 서비스 개통 때만 true |
| `NEWSLETTER_SEND_ENABLED` | 기본 미설정/false, 운영 발송 별도 개통 때만 true |
| `DB` | 전용 D1 binding |
| `SITE_ORIGIN` | `https://dowwalabs.com` 고정, preview는 운영 연결 금지 |
| `MAIL_FROM` | 검증한 발신 도메인의 주소와 이름. 아직 사용자 미정 |
| `RESEND_API_KEY` | 발송 전용 서버 비밀키 |
| `RATE_LIMIT_SALT` | 무작위 32자 이상, IP 해싱 |
| `UNSUBSCRIBE_SIGNING_KEY` | 무작위 32자 이상, 해지 링크 HMAC, 기존 발송의 해지를 위해 지속 보관 |
| `NEWSLETTER_ADMIN_TOKEN` | 무작위 32자 이상, 서버 전용 운영자 토큰 |
| `PRIVACY_READY` | 실제 개인정보 처리·대행사·수신 안내 정리 후 true |
| `SENDER_FOOTER` | 확정한 발신 사업자·연락처·주소 정보 |
| `CONFIRM_HOURLY_LIMIT` | 기본 최대 50건/시간, 필요 시 낮춰서 시작 |

신청 폼을 통해 이메일 주소가 메일 공급자로 전달되므로, 실제 발송에 앞서 사용자에게 공급자·발신 주소·대상·비용을 명시한다. 기존 회원 이메일을 수신 동의 없이 불러오지 않는다.

## 칼럼 공개와 발송

1. `data/newsletter-issues.mjs`에 사용자가 승인한 칼럼을 등록한다. `kind:'column', approved:true, published:true`여야 공개 보관함과 발송에 포함된다. ID는 재사용하거나 기존 발송 후 내용을 바꾸지 않는다.
2. 배포 전 발행 원고를 확인한다. 공개 보관함의 발행과 이메일 발송은 별도 작업이다.
3. 서버 비밀값을 안전하게 로드한 운영 환경에서 `node scripts/newsletter-send.mjs --plan ISSUE_ID`를 실행하면 제목·본문·수신자 수·본문 fingerprint만 보여준다. 실제 이메일 주소 목록은 출력하지 않는다.
4. 사용자에게 원고와 수신 범위를 보여주고 실제 발송 승인을 받은 뒤 `--send ISSUE_ID --approve FINGERPRINT`로 실행한다. 승인 fingerprint가 일치해야 하고 서버 발송 플래그도 필요하다.
5. 10명 단위 처리. 같은 issue/subscriber는 DB 유일키로 한 번만 claim한다. 공급자 API에 같은 idempotency key를 전달한다.
6. 공급자 실패/타임아웃/DB 기록 실패 시 `uncertain`으로 멈춘다. 자동으로 재시도하지 않는다. 공급자 기록과 대조한 뒤 별도 복구 판단이 필요하다.

## 운영 전 남은 필수 작업

- 현재 운영 배포 접근권한 확보 또는 도완님 소유 호스팅 이전 결정. 계정 생성·도메인 DNS 변경·유료 결제를 아직 하지 않았다.
- 발신 이름/주소, 도메인 인증, 실제 발송 서비스와 예산 확정.
- 사업자/발신자 표기 및 동의·개인정보 안내 최종 확정. 개인정보 안내의 준비 문구를 실제 처리 기준으로 바꾼다. 해지 시 발송 중단은 구현했지만 이메일/동의 기록의 보관·삭제 정책은 아직 운영하지 않는다.
- 공급자 bounce/complaint 웹훅과 억제 목록 반영, 메일 도달 테스트. 현재 webhook 미구현이므로 대량 발송 활성화 금지.
- 공개 API 호스트의 방어와 한도 확인. 기본 시간당 한도만으로 운영 예산이 보장되지는 않는다.
- 실제 D1의 Functions 결합 검증. 로컬 SQLite 테스트를 실제 운영 클라우드 검증으로 간주하지 않는다.
- 담당자가 직접 칼럼을 작성하는 관리자 편집 화면은 후속 범위. 첫 버전은 검토한 원고 파일과 운영자 도구로 공개/발송한다.
- 주간 자동 모음·예약 발송은 이번 버전에 포함하지 않는다. 주기·대상·포함 칼럼을 정한 후 추가한다.
